# Claude Code Foundation - 実用ガイド

## クイックスタート

### 1. 基本的な開発フロー

新機能を開発する際の標準的なフローです。

```
① 要件定義 → ② 非機能要件 → ③ スコープ → ④ 設計 → ⑤ タスク分解 → ⑥ 実装・レビュー → ⑦ リリース
```

各段階で**必ず承認**を得てから次に進みます。

### 2. 最初の一歩

```bash
# プロジェクトディレクトリに移動
cd your-project

# Claudeと会話を開始
# まずは要件定義から
/skill:requirements-definition
```

## シナリオ別の使い方

### シナリオ1: 新機能を開発する（フルフロー）

#### Step 1: 要件定義
```
あなた: /skill:requirements-definition
```

Claude: 対話形式で以下を聞いてきます：
- 背景・目的
- ユーザー・利用シーン
- 機能詳細
- 制約条件

**出力例:**
```markdown
# 要件定義書: ユーザー認証機能

## 1. 概要
### 1.1 背景
既存システムにログイン機能が存在せず、すべてのユーザーが同じ権限で操作している。

### 1.2 目的
ユーザーごとに権限を分け、セキュアなアクセス制御を実現する。

## 3. 機能要件
### 3.1 機能一覧
| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| FR-001 | メールログイン | メールアドレスとパスワードでログイン | Must |
| FR-002 | パスワードリセット | メール経由でパスワードをリセット | Must |
| FR-003 | OAuth連携 | Google/GitHubでログイン | Nice |

### 3.2 機能詳細
#### FR-001: メールログイン
- **説明**: メールアドレスとパスワードでログイン
- **入力**: メールアドレス、パスワード
- **出力**: JWTトークン
- **受入条件（AC）**:
  - [ ] 正しい認証情報でログインできる - 確認方法: API /auth/login に POST
  - [ ] 間違った認証情報で401エラーが返る - 確認方法: API /auth/login に POST
  - [ ] 5回連続失敗でアカウントロック - 確認方法: ログ確認
```

**👉 承認ポイント①**: 要件定義が完了したら承認

#### Step 2: 非機能要件定義
```
あなた: /skill:non-functional-requirements
```

Claude: 以下を定義します：
- 性能要件（レスポンスタイム、同時接続数）
- セキュリティ要件（暗号化、監査ログ）
- 可用性要件（ダウンタイム許容値）
- データ機微度（個人情報の取り扱い）

**出力例:**
```markdown
## 性能要件
- ログインAPIのレスポンスタイム: 500ms以内（P95）
- 同時ログイン数: 1000ユーザー/分

## セキュリティ要件
- パスワードはbcryptでハッシュ化（コスト係数10）
- JWTトークンの有効期限: 24時間
- 監査ログ: ログイン試行（成功/失敗）をすべて記録

## 可用性要件
- 稼働率: 99.9%（月間ダウンタイム43分以内）
- RPO: 1時間、RTO: 4時間
```

**👉 承認ポイント②**: 非機能要件が完了したら承認

#### Step 3: スコープ定義
```
あなた: /skill:scope-definition
```

Claude: スコープ内/外を明確化します。

**出力例:**
```markdown
## スコープ内
- メールログイン機能（FR-001）
- パスワードリセット機能（FR-002）
- ログイン試行の監査ログ

## スコープ外
- OAuth連携（FR-003）→ v2.0で実装
- 2要素認証 → v3.0で検討
- パスワードポリシー設定画面 → 現時点では固定値
```

**👉 承認ポイント③**: スコープが完了したら承認

#### Step 4: 設計レビュー
```
あなた: /skill:design-review
```

Claude: 以下を確認・設計します：
- アーキテクチャ選定
- エラーハンドリング設計
- 運用設計（ログ・監視・切り戻し）

**👉 承認ポイント④**: 設計が完了したら承認

#### Step 5: タスク分解
```
あなた: /skill:task-breakdown
```

Claude: 1タスク=1PR単位でタスクを分解します。

**出力例:**
```markdown
## タスクリスト

### Phase 1: 基盤整備
- [ ] TASK-001: データベーススキーマ作成（usersテーブル） #123
  - **Done条件**: マイグレーションファイルが作成され、実行できる
  - **確認方法**: `npm run migrate` が成功する

- [ ] TASK-002: JWTライブラリのセットアップ #124
  - **Done条件**: JWTトークンの生成・検証ができる
  - **確認方法**: ユニットテストが通る

### Phase 2: API実装
- [ ] TASK-003: POST /auth/register 実装 #125
  - **Done条件**: 新規ユーザー登録ができる
  - **確認方法**: Postmanで201が返る

- [ ] TASK-004: POST /auth/login 実装 #126
  - **Done条件**: ログインしてJWTトークンが取得できる
  - **確認方法**: Postmanで200とトークンが返る

- [ ] TASK-005: アカウントロック機能実装 #127
  - **Done条件**: 5回連続失敗でロックされる
  - **確認方法**: テストケースが通る
```

**👉 承認ポイント⑤**: タスク分解が完了したら承認

#### Step 6: 実装・レビュー

ここからは推奨スキルが自動で使われます。

```

- ベストプラクティスの確認
```

**👉 承認ポイント⑥**: 実装・レビューが完了したら承認

#### Step 7: リリース計画
```

```

Claude: リリース手順と切り戻し手順を作成します。

**👉 承認ポイント⑦**: リリース計画が完了したら承認

## エージェントの活用

### 3つのサブエージェント

スキルとは別に、品質保証・進捗管理・技術調査を担う3つのサブエージェントが用意されています。

| Agent | 役割 | 使用タイミング |
|-------|------|---------------|
| `qa-general` | 成果物の品質チェック | レビュー依頼時、QC実施時 |
| `status-updater` | 進捗状況の追跡・更新 | フェーズ完了時、進捗確認時 |
| `web-researcher` | 技術情報の検証・調査 | API仕様確認、ライブラリ調査時 |

### qa-general（品質保証エージェント）

成果物（ドキュメント・コード・設計）の品質チェックを行います。

```
あなた: 品質チェックして

Claude: [qa-generalエージェントが発動]
- 各スキルのevaluation_criteria.mdを参照
- 構造チェック（Pass/Fail）
- 内容チェック（スコアリング）
- 最終判定（Pass/Conditional Pass/Fail）
```

**出力例:**
```
### QC結果: Pass
スコア: 85/100

#### 指摘事項
1. [ドキュメント]: 曖昧表現「適切に」を具体化 (重要度: Medium)

#### 修正推奨
- 「適切にバリデーション」→「入力値を正規表現でチェック」
```

### web-researcher（技術調査エージェント）

技術情報の検証・調査を行います。

```
あなた: Stripe APIの最新仕様を調査して

Claude: [web-researcherエージェントが発動]
- 公式ドキュメント優先で検索
- 情報の確度（高/中/低）を判定
- ソースURLを付記して報告
```

### 評価基準（Evaluation Criteria）

各スキルには `evaluation/evaluation_criteria.md` が用意されており、qa-generalエージェントはこれを参照して品質判定を行います。

**評価の仕組み:**

| 区分 | チェック内容 | 判定 |
|------|-------------|------|
| 構造チェック | 必須セクション・Critical項目の有無 | Pass/Fail |
| 内容チェック | 中身の質（100点満点） | スコアリング |

**最終判定:**
- **Pass**: 全Criticalチェック項目がPass かつ スコア80点以上
- **Conditional Pass**: 全Criticalチェック項目がPass かつ スコア60-79点
- **Fail**: CriticalチェックにFailあり または スコア60点未満

## ベストプラクティス

### 1. 承認ポイントを必ず守る

```
❌ 悪い例:
あなた: 認証機能を実装して

Claude: [いきなり実装を開始]
```

```
✅ 良い例:
あなた: /skill:requirements-definition
→ 要件定義 → 承認
あなた: /skill:non-functional-requirements
→ 非機能要件 → 承認
あなた: /skill:scope-definition
→ スコープ → 承認
あなた: /skill:design-review
→ 設計 → 承認
あなた: /skill:task-breakdown
→ タスク分解 → 承認
あなた: TASK-001から実装して
→ 実装開始
```

### 2. 曖昧語を使わない

```
❌ 悪い例:
「適切にエラーハンドリングして」
「なるべく早くレスポンスを返して」
「よしなに実装して」
```

```
✅ 良い例:
「タイムアウトは3秒、3回リトライ後に500エラーを返す」
「レスポンスタイムは500ms以内（P95）」
「仕様書の通りに実装して」
```

### 3. スコープ内/外を明確にする

```
❌ 悪い例:
「ログイン機能を実装」
```

```
✅ 良い例:
【スコープ内】
- メールログイン（FR-001）
- パスワードリセット（FR-002）

【スコープ外】
- OAuth連携（v2.0で実装）
- 2要素認証（v3.0で検討）
```

### 4. AC（受入条件）はYes/No判定可能にする

```
❌ 悪い例:
- ログインできること
```

```
✅ 良い例:
- [ ] 正しい認証情報でログインできる - 確認方法: API /auth/login に POST して200が返る
- [ ] 間違った認証情報で401エラーが返る - 確認方法: API /auth/login に POST して401が返る
```

### 5. 1タスク=1PR

```
❌ 悪い例:
TASK-001: 認証機能実装（登録、ログイン、ログアウト、パスワードリセット）
```

```
✅ 良い例:
TASK-001: ユーザー登録API実装 #123
TASK-002: ログインAPI実装 #124
TASK-003: ログアウトAPI実装 #125
TASK-004: パスワードリセットAPI実装 #126
```

### 6. 失敗時挙動を先に設計する

```
❌ 悪い例:
「APIを実装して」→ 後からタイムアウト処理を追加
```

```
✅ 良い例:
【設計時に決める】
- タイムアウト: 3秒
- リトライ: 3回（指数バックオフ）
- エラーレスポンス: {"error": "timeout", "code": "E001"}
- ログレベル: ERROR
→ この仕様で実装
```

## よくある質問（FAQ）

### Q1. 推奨スキルと壁打ちスキルの違いは？

**A:**
- **推奨スキル**: 自動で呼び出される。日常的な開発作業で使う。
- **壁打ちスキル**: 明示的に呼び出す。プロジェクト開始時や重要な意思決定で使う。

### Q2. 承認ポイントをスキップしてもいい？

**A:**
小規模な修正（typo修正、ログ追加など）であればスキップ可能です。ただし、新機能追加や設計変更の場合は必ず承認ポイントを通過してください。

### Q3. スキルが自動で発動しない場合は？

**A:**
明示的にスキルを呼び出すことができます。

```
あなた: /skill:code-review でsrc/auth/login.tsをレビューして
```

### Q4. CLAUDE.mdをカスタマイズしてもいい？

**A:**
可能です。ただし、18の普遍原則は普遍的なルールなので、できるだけ変更しないことを推奨します。プロジェクト固有のルールは `.claude/CLAUDE.local.md` に追加してください。

### Q5. 複数プロジェクトで異なる設定を使いたい

**A:**
以下の優先順位で設定が読み込まれます：

1. `プロジェクトルート/.claude/` (プロジェクト固有)
2. `プロジェクトルート/CLAUDE.md` (プロジェクト固有)
3. `~/.claude/` (ユーザー全体のデフォルト)

プロジェクトごとに `.claude/` を作成すれば、個別設定が可能です。

### Q6. テストが失敗したとき、実装を変更してもいい？

**A:**
**絶対に禁止です**（普遍原則#17）。テストは「検証手段」であり、実装を曲げるものではありません。

```
❌ 悪い例:
テスト失敗 → 実装を変更してテストを通す
```

```
✅ 良い例:
テスト失敗 → 仕様を再確認 → 実装が間違っていれば修正 / テストが間違っていればテストを修正
```

## トラブルシューティング

### Hooksが動作しない

**症状:**
ファイル保存時に自動フォーマットが動作しない。

**原因:**
- Python3がインストールされていない（HooksはPython3で実装）
- Prettierがインストールされていない
- `settings.json` が正しく配置されていない

**解決策:**
```bash
# Python3がインストールされているか確認
python3 --version
# Windowsの場合
python --version

# Prettierをインストール
npm install --save-dev prettier

# settings.jsonを確認
cat .claude/settings.json
```

### 機密ファイルがブロックされない

**症状:**
`.env` ファイルが読めてしまう。

**原因:**
- Hooksが有効になっていない
- `settings.json` の `permissions` が設定されていない

**解決策:**
```bash
# settings.jsonを確認
cat .claude/settings.json

# permissionsセクションを確認
jq '.permissions' .claude/settings.json
```

### スキルが自動で呼び出されない

**症状:**
「コードレビューして」と言っても、スキルが発動しない。

**原因:**
- スキルの `description` にトリガー条件が書かれていない
- スキルファイルが正しい場所にない

**解決策:**
```bash
# スキルファイルの場所を確認
ls -la .claude/skills/

# スキルのdescriptionを確認
head -n 5 .claude/skills/code-review/SKILL.md
```

**Claude Code Foundation**を使うことで、以下が実現できます：

✅ AIに丸投げせず、人間が意思決定に関与（Human in the Loop）
✅ 曖昧さを排除し、具体的な仕様で開発
✅ 失敗時の挙動を先に設計し、本番障害を予防
✅ 運用まで見据えた設計（ログ・監視・切り戻し）
✅ 標準化されたワークフローで、どのプロジェクトでも同じ品質を維持

まずは小さな機能から試してみて、慣れてきたらフルフローで使ってみてください。
