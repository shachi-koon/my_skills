# お問い合わせ管理基盤SaaS インフラ・運用設計書

## 0. 設計選択理由（決定ログ）

| 選択 | 理由 | 再検討条件 |
|------|------|-----------|
| ECS Fargate | サーバーレス、スケーリング容易、運用負荷低減 | 大規模時はEKSへの移行を検討 |
| Blue-Greenデプロイ | ダウンタイムなし、即時切り戻し可能 | カナリアリリースはフェーズ2以降で検討 |
| AWS CDK（TypeScript） | インフラをコードで管理、型安全、テスト可能 | Terraformへの移行はマルチクラウド対応時のみ |
| GitHub Actions | GitHubリポジトリとの親和性、マーケットプレイスの豊富なAction | AWS CodePipelineへの移行はAWSネイティブ化が必要な場合 |

## 2. デプロイ方式

### 2.1 Blue-Greenデプロイメント

**フロー**
1. 新バージョンをGreen環境にデプロイ
2. ヘルスチェック通過を確認
3. ALBのターゲットグループを切り替え
4. 旧バージョン（Blue）を15分間維持（切り戻し用）
5. 問題なければBlue環境を更新

**GitHub Actionsワークフロー**
```yaml
deploy:
  steps:
    - name: Deploy to Green
    - name: Wait for health check (5 min timeout)
    - name: Switch ALB target group
    - name: Wait for validation (15 min)
    - name: Update Blue (or rollback)
```

### 2.2 切り戻し手順

**担当**: オンコール担当者
**判断基準**: エラー率5%超過、レイテンシ1秒超過、ユーザー報告

#### 切り戻しフロー（自動）
| ステップ | 操作 | 担当 | 所要時間 |
|---------|------|------|---------|
| 1 | CloudWatch Alarmでアラート発火 | 自動 | 即時 |
| 2 | Slack/PagerDutyで通知 | 自動 | 30秒 |
| 3 | 担当者がダッシュボードで状況確認 | 人間 | 1-2分 |
| 4 | 切り戻し判断 | 人間 | - |
| 5 | GitHub Actions: rollbackワークフロー実行 | 人間→自動 | 2分 |
| 6 | ALBターゲットグループをBlueに切り替え | 自動 | 30秒 |
| 7 | 切り戻し完了確認 | 人間 | 1分 |

**合計所要時間**: 5-7分

#### 切り戻しコマンド
```bash
# GitHub Actions経由
gh workflow run rollback.yml -f environment=production -f reason="High error rate"

# 緊急時（AWS CLI直接）
aws ecs update-service --cluster inquiry-prod --service api --task-definition api:PREVIOUS_VERSION
aws elbv2 modify-listener --listener-arn $ALB_LISTENER_ARN --default-actions Type=forward,TargetGroupArn=$BLUE_TG_ARN
```

#### 切り戻し後の対応
1. 障害報告書を作成（30分以内に速報）
2. 原因調査開始
3. 修正版の作成・テスト
4. 再デプロイ計画の策定

### 2.3 DBマイグレーション

**原則**
- 後方互換性のある変更のみ（カラム追加、インデックス追加）
- 破壊的変更（カラム削除、型変更）は2段階デプロイ

**手順**
1. マイグレーションスクリプトをレビュー
2. ステージング環境で実行・検証
3. 本番環境でマイグレーション実行（メンテナンス時間外可能な場合）
4. アプリケーションデプロイ

**切り戻し**
- 各マイグレーションに`down`スクリプトを用意
- 実行前にDBスナップショットを取得

## 4. 定期ジョブ（バッチ処理）

### 4.1 ジョブ一覧

| ジョブ名 | 実行タイミング | 対応機能 | 概要 |
|---------|--------------|---------|------|
| 自動完了確認メール送信 | 毎時0分 | FR-A004 | 回答済み+72時間経過の問い合わせに確認メール送信 |
| 自動完了処理 | 毎時0分 | FR-A004 | 確認メール送信後1週間経過の問い合わせを完了に遷移 |
| 期限超過アラート | 毎時0分 | FR-A005 | 期限超過の問い合わせを検知しアラートメール送信 |
| 期限間近アラート | 毎時0分 | FR-A005 | 期限24時間以内の問い合わせに事前通知 |
| 長期滞留アラート | 毎日9:00 | FR-A005 | 72時間更新なしの問い合わせをサービス管理者に通知 |
| 日次ダイジェスト | 毎日9:00 | 5.3通知設定 | 日次ダイジェスト設定ユーザーへまとめ通知 |

### 4.2 実行基盤

| 項目 | 設定値 |
|------|--------|
| 実行環境 | Amazon EventBridge Scheduler + ECS Fargate (Scheduled Task) |
| タイムアウト | 300秒（5分） |
| メモリ | 512MB |
| CPU | 0.25 vCPU |
| 同時実行数 | 1（排他制御あり） |

### 4.3 失敗時挙動

#### リトライポリシー

| ジョブ種別 | リトライ回数 | リトライ間隔 | 最大実行時間 |
|-----------|------------|-------------|-------------|
| メール送信系 | 3回 | 5分（固定） | 15分 |
| ステータス更新系 | 3回 | 1分（指数バックオフ） | 10分 |
| アラート系 | 2回 | 5分（固定） | 10分 |

#### 失敗通知

| 条件 | 通知先 | 通知方法 | 内容 |
|------|--------|---------|------|
| リトライ上限到達 | 開発チーム | Slack #alerts | ジョブ名、失敗時刻、エラーメッセージ、対象件数 |
| タイムアウト | 開発チーム | Slack #alerts + PagerDuty | ジョブ名、開始時刻、タイムアウト時刻 |
| 連続3回失敗 | 開発チーム | PagerDuty | ジョブ名、失敗履歴、緊急対応要請 |

#### 監視設定

```yaml
# CloudWatch Alarm設定
AutoCompletionJobFailure:
  MetricName: JobExecutionFailed
  Dimensions:
    - Name: JobName
      Value: auto-completion
  Threshold: 1
  Period: 3600  # 1時間
  EvaluationPeriods: 1
  AlarmActions:
    - !Ref SlackNotificationTopic
```

#### 障害発生時の対応手順

| ステップ | 操作 | 担当 | 所要時間 |
|---------|------|------|---------|
| 1 | CloudWatch Alarmでアラート発火 | 自動 | 即時 |
| 2 | Slackで通知受信 | 自動 | 30秒 |
| 3 | CloudWatch Logsでエラー詳細確認 | 開発者 | 5分 |
| 4 | 原因特定（DB接続、SES障害、ロジックバグ等） | 開発者 | 10-30分 |
| 5 | 修正 or 手動リカバリ実行 | 開発者 | 状況による |
| 6 | 手動でジョブ再実行（必要な場合） | 開発者 | 5分 |

#### 手動実行コマンド

```bash
# 自動完了確認メール送信の手動実行
aws ecs run-task \
  --cluster inquiry-prod \
  --task-definition batch-auto-completion-reminder \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[subnet-xxx],securityGroups=[sg-xxx]}"

# 特定テナントのみ対象にする場合
aws ecs run-task \
  --cluster inquiry-prod \
  --task-definition batch-auto-completion-reminder \
  --launch-type FARGATE \
  --overrides '{"containerOverrides":[{"name":"batch","environment":[{"name":"TARGET_TENANT_ID","value":"tnt_xxx"}]}]}'
```

## 5. 災害復旧（DR）

### 5.1 バックアップ

| 対象 | 方式 | 頻度 | 保持期間 |
|------|------|------|---------|
| Aurora | 自動バックアップ | 継続的 | 7日 |
| Aurora | 手動スナップショット | 週次 | 30日 |
| S3（添付ファイル） | バージョニング | 常時 | 無期限 |
| S3（添付ファイル） | クロスリージョンレプリケーション | 常時 | 無期限 |

### 5.2 復旧目標

| 指標 | 目標値 |
|------|--------|
| RPO（目標復旧時点） | 1時間 |
| RTO（目標復旧時間） | 4時間 |

### 5.3 復旧手順

1. 障害発生の検知・報告
2. 影響範囲の特定
3. 復旧方式の決定（スナップショット復元 or フェイルオーバー）
4. Aurora: ポイントインタイムリカバリ or スナップショット復元
5. S3: バージョン復元 or クロスリージョンからコピー
6. アプリケーション再起動
7. 動作確認
8. サービス再開通知
