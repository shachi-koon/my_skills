# Claude Code Foundation - 思想と実現内容

## 1. 概要

**Claude Code Foundation**は、スペック駆動開発（SDD: Spec Driven Development）を実現するためのClaude Code基盤設定集です。個人開発・チーム開発の両方に対応し、AIエージェントと人間が協調しながら高品質なソフトウェアを開発するための「ルール」「ワークフロー」「セーフティネット」を提供します。

### 核心的な価値

- **曖昧さの排除**: 「適切に」「よしなに」などの曖昧語を禁止し、具体的な数値・条件・手順で開発を進める
- **Human in the Loop**: AIに丸投げせず、7つの承認ポイントで人間が意思決定に関与
- **失敗への備え**: 正常系よりも失敗時の挙動を先に設計する思想
- **軽量さの維持**: コンテキストを肥大化させず、必要な時だけ必要な情報を引き出す

## 2. 基本思想

### 2.1 スペック駆動開発（SDD）とは

従来の開発フローを逆転させる思想です。

**従来のフロー:**
```
実装 → テスト → 仕様書（後追い）
```

**SDDのフロー:**
```
仕様書（先行） → 実装 → テスト（検証）
```

仕様を先に固めることで、以下を実現します：
- AIエージェントが迷わず実装できる
- 人間は「何を作るか」に集中できる
- テストは「検証手段」として機能する（実装を曲げない）

### 2.2 3つの設計原則

#### ① 失敗時挙動先行
成功パスよりも失敗パスを先に設計します。
- タイムアウト値
- リトライ回数
- エラーハンドリング
- ログ方針

**理由**: 本番環境で問題が起きるのは失敗時。後から追加すると設計全体が崩れる。

#### ② 非機能先行
機能要件の前に非機能要件を固めます。
- 性能要件（レスポンスタイム、スループット）
- 監査ログ（何をどこまで記録するか）
- 可用性（ダウンタイム許容値）
- データ機微度（個人情報の取り扱い）

**理由**: 非機能は後から追加できない。アーキテクチャ全体に影響する。

#### ③ 運用設計必須
「作って終わり」ではなく、運用まで設計します。
- ログ・監視・アラート
- 切り戻し手順
- 障害対応フロー

**理由**: 運用できないシステムは価値を生まない。

## 3. 構成要素の分類

### スキルの3分類（思想的な分類）

| 分類 | 役割 | 変更頻度 | 例 |
|------|------|---------|-----|
| **普遍原則** | どのプロジェクトでも守るルール | ほぼ変えない | 「曖昧語禁止」「1タスク=1PR」 |
| **推奨スキル** | お任せ時に自動発動する | たまに更新 | 「コードレビュー」「アーキテクチャ選定」 |
| **壁打ちスキル** | 明示的に呼び出して対話で決める | 毎回使う | 「要件定義」「スコープ定義」 |

### ファイル配置の2層構造（公式の構成）

| レベル | パス | 用途 | Git管理 |
|--------|------|------|---------|
| **ユーザーレベル** | `~/.claude/` | 全プロジェクトで使う基盤 | しない（個人用） |
| **プロジェクトレベル** | `./.claude/` | プロジェクト固有の設定 | する（チーム共有） |
| **プロジェクトローカル** | `./.claude/*.local.*` | 個人的な上書き設定 | しない（gitignore） |

**優先順位**: プロジェクト > ユーザー（プロジェクト設定が優先される）

### 普遍原則（CLAUDE.md）
18項目の不変ルール。すべてのプロジェクトで適用されます。
- 60行以下に収める（軽量さの維持）
- Always読み込み（常に有効）

### 推奨スキル（8個）
通常の会話で自動的に呼び出されるスキル。
- `sdd-workflow`: 仕様駆動開発の進め方
- `architecture-selection`: アーキテクチャ選定
- `code-review`: コードレビュー
- `explore-codebase`: コードベース調査
- `document-generator`: ドキュメント生成
- `git-workflow`: Gitワークフロー
- `error-handling-design`: エラーハンドリング設計
- `test-verification`: テスト検証

### 壁打ちスキル（6個）
明示的に呼び出して、対話形式で決めるスキル。
- `/skill:requirements-definition`: 要件定義
- `/skill:non-functional-requirements`: 非機能要件
- `/skill:scope-definition`: スコープ定義
- `/skill:design-review`: 設計レビュー
- `/skill:task-breakdown`: タスク分解
- `/skill:release-planning`: リリース計画

## 4. 18の普遍原則

### 言語・表現（2項目）
| # | 原則 | 理由 |
|---|------|------|
| 1 | 曖昧語禁止（適切に/なるべく/よしなに） | AIも人間も解釈がブレる |
| 2 | 用語統一（日本語ベース） | 英語のみのラベルは避ける |

### ドキュメント品質（3項目）
| # | 原則 | 理由 |
|---|------|------|
| 3 | AC記述ルール（Yes/No判定可能） | 「確認方法」とセットで記載 |
| 4 | スコープ明記 | 「スコープ」「スコープ外」を両方記載 |
| 5 | 未決事項管理 | 責任者・期限・承認ポイントを明記 |

### 設計（3項目）
| # | 原則 | 理由 |
|---|------|------|
| 6 | 失敗時挙動先行 | タイムアウト/リトライ/エラーハンドリングを実装前に決定 |
| 7 | 非機能先行 | 性能・監査ログ・可用性を要件定義で固定 |
| 8 | 運用設計必須 | ログ/監視/切り戻し手順を実行可能なレベルで残す |

### タスク管理（5項目）
| # | 原則 | 理由 |
|---|------|------|
| 9 | 1タスク=1PR | 各タスクに「確認方法」「Done条件」を記載 |
| 10 | タスク紐付け必須 | すべての変更はチケットに紐付ける |
| 11 | 変更経緯の記録 | 「何を・なぜ・どう変えたか」を残す |
| 12 | 影響範囲の明記 | 変更による影響範囲を記録 |
| 13 | コミットメッセージ規約 | チケット番号を含める（例：`feat: ログイン機能追加 #123`） |

### 判断・意思決定（2項目）
| # | 原則 | 理由 |
|---|------|------|
| 14 | 決定ログ | 重要決定は「誰が・なぜ・再検討条件」を残す |
| 16 | 3年目基準 | 経験3年目のエンジニアが読めば実装できるレベルまで分解 |

### リリース・テスト・コンテキスト（3項目）
| # | 原則 | 理由 |
|---|------|------|
| 15 | 手順と切り戻しはセット | 担当・順序・確認観点・切り戻し手順を必ず定義 |
| 17 | テスト改変禁止 | テストを通すための実装改修は絶対禁止 |
| 18 | コンテキスト軽量維持 | Always読み込みは最小限、重い観点はManualで呼ぶ |

## 5. 7つの承認ポイント（Human in the Loop）

AIエージェントに丸投げせず、人間が意思決定に関与する7つのゲート。

```
①要件定義 → [承認] → ②非機能要件 → [承認] → ③スコープ → [承認]
    ↓
④設計 → [承認] → ⑤タスク分解 → [承認] → ⑥実装・レビュー → [承認] → ⑦リリース → [承認]
```

### 各承認ポイントの役割

| # | ポイント | 確認内容 | スキル |
|---|----------|---------|--------|
| ① | 要件定義完了 | 機能要件が明確か、曖昧語がないか | `requirements-definition` |
| ② | 非機能要件確定 | 性能、監査ログ、可用性が定義されているか | `non-functional-requirements` |
| ③ | スコープ確定 | スコープ内/外が明確か、未決事項が管理されているか | `scope-definition` |
| ④ | 設計確定 | 失敗時挙動、エラーハンドリング、運用設計が完了しているか | `design-review` |
| ⑤ | タスク確定 | 1タスク=1PRに分解され、Done条件が明確か | `task-breakdown` |
| ⑥ | 実装・レビュー完了 | コードレビューが完了し、テストが通っているか | `code-review`, `test-verification` |
| ⑦ | リリース承認 | リリース手順と切り戻し手順が定義されているか | `release-planning` |

**重要:** 承認なしでは次工程に進まない。

## 7. セーフティネット（Hooks）

### 7.1 PreToolUse Hooks（実行前チェック）

#### 機密ファイル保護
```json
{
  "matcher": "Edit|Write|Read",
  "hooks": [
    {
      "type": "command",
      "command": "...",
      "timeout": 5
    }
  ]
}
```

**ブロック対象:**
- `.env`, `.env.local`, `.env.production`
- `/secrets/`, `/credentials/`, `.secret`

#### 危険なコマンド保護
```json
{
  "matcher": "Bash",
  "hooks": [...]
}
```

**ブロック対象:**
- `rm -rf /`, `rm -rf ~`, `rm -rf .`
- `> /dev/sda`
- `:(){:|:&};:` (Fork Bomb)

### 7.2 PostToolUse Hooks（実行後処理）

#### 自動フォーマット
ファイル編集・作成後に自動でPrettierを実行。
- 対象: `.ts`, `.tsx`, `.js`, `.jsx`, `.json`, `.md`

#### 型チェック
TypeScriptファイル編集後に自動で型チェック。
- 対象: `.ts`, `.tsx`
- エラーがあれば最初の20行を表示

### 7.3 Permissions（権限管理）

#### 許可リスト
- `Read`, `Glob`, `Grep`
- `Bash(npm run:*)`, `Bash(npx:*)`
- `Bash(git status:*)`, `Bash(git diff:*)`, `Bash(git log:*)`, `Bash(git branch:*)`

#### 拒否リスト
- `Read(./.env)`, `Read(./.env.*)`
- `Read(./secrets/**)`, `Read(./credentials/**)`
- `Write(./package-lock.json)`, `Write(./yarn.lock)`
- `Bash(rm -rf:*)`

| 項目 | 目標値 | 理由 |
|------|--------|------|
| CLAUDE.md | 60行以下 | コンテキスト軽量化 |
| SKILL.md | 5,000 words以下 | スキル1つあたりの情報量上限 |
| 同時有効スキル | 20-50個以下 | トリガー精度維持 |
| 有効MCP | 10個以下 | 複雑性の制御 |

| テストカバレッジ | 80%以上 | 品質保証 |

## 9. 実現されること

### 9.1 開発プロセスの標準化
- AIエージェントと人間が共通のルールで開発を進める
- どのプロジェクトでも同じワークフローが適用される
- チーム間での認識のズレが減少

### 9.2 品質の担保
- 曖昧さを排除し、Yes/No判定可能な受入条件を定義
- 失敗時挙動を先に設計することで、本番障害を予防
- テストは「検証手段」として機能（実装を曲げない）

### 9.3 AIと人間の役割分担
- **AIエージェント**: 仕様に基づいた実装、コードレビュー、ドキュメント生成
- **人間**: 要件定義、承認、重要な意思決定
- Human in the Loopにより、AIに丸投げしない開発を実現

### 9.4 運用まで見据えた設計
- ログ・監視・アラート・切り戻し手順を必ず定義
- 運用できないシステムは作らない
- 障害時の対応フローまで設計段階で決める

### 9.5 軽量さの維持
- CLAUDE.mdは60行以下に収める
- Always読み込みは最小限、重い観点はManualで呼ぶ
- コンテキストを肥大化させず、必要な時だけ情報を引き出す

### 9.6 セーフティネット
- 機密ファイルへのアクセスをブロック
- 危険なコマンドの実行を防止
- 自動フォーマット・型チェックで品質を維持

### 9.7 柔軟な配置構造（公式2層モデル）
- **ユーザーレベル**（`~/.claude/`）：全プロジェクトで使う基盤
- **プロジェクトレベル**（`./.claude/`）：プロジェクト固有の設定をチーム共有
- **ローカル上書き**（`*.local.*`）：個人的なカスタマイズ（gitignore）
- プロジェクト設定がユーザー設定を上書き（優先順位が明確）

## 10. まとめ

**Claude Code Foundation**は、単なる設定ファイルの集まりではなく、以下を実現する「開発思想のパッケージ」です：

1. **曖昧さの排除** - 「適切に」「よしなに」を禁止し、具体的に開発
2. **失敗への備え** - 失敗時の挙動を先に設計
3. **Human in the Loop** - 7つの承認ポイントで人間が意思決定に関与
4. **運用まで見据える** - ログ・監視・切り戻し手順を必ず定義
5. **軽量さの維持** - コンテキストを肥大化させない
6. **セーフティネット** - Hooksで自動化と保護を実現

このフレームワークを使うことで、AIエージェントと人間が協調しながら、高品質で運用可能なソフトウェアを効率的に開発できます。
