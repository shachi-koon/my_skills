# アーキテクチャ選定

## 概要
選択肢を比較し、トレードオフを整理して意思決定を支援する。最終判断は人が行う。

## 選定プロセス

### Step 1: 要件の整理
以下を明確にする：
- 機能要件の概要
- 非機能要件（性能、可用性、セキュリティ）
- 制約条件（予算、期間、チームスキル）
- 将来の拡張性要件

### Step 2: 選択肢の列挙
最低3つの選択肢を提示する。

**システムアーキテクチャの例:**
- モノリス
- マイクロサービス
- モジュラーモノリス

**アプリアーキテクチャの例:**
- 4層アーキテクチャ（Presentation/Application/Domain/Infrastructure）
- クリーンアーキテクチャ
- MVVM / MVC / MVP

**インフラアーキテクチャの例:**
- サーバーレス（Lambda + API Gateway）
- コンテナ（ECS / EKS）
- 従来型（EC2）

### Step 3: 比較表の作成

| 観点 | 選択肢A | 選択肢B | 選択肢C |
|------|--------|--------|--------|
| 初期コスト | | | |
| 運用コスト | | | |
| 開発速度 | | | |
| スケーラビリティ | | | |
| 学習コスト | | | |
| 保守性 | | | |
| チーム適合性 | | | |

### Step 4: トレードオフの整理
各選択肢の「得るもの」と「失うもの」を明記。

```
選択肢A: ○○
  得るもの: シンプルさ、開発速度
  失うもの: スケーラビリティ、柔軟性
  適するケース: MVP、小規模チーム
```

### Step 5: 推奨案の提示
根拠とともに推奨案を提示。ただし最終判断は人が行う。

## 承認ポイント
アーキテクチャ決定は設計フェーズの承認ポイントで確定する。
