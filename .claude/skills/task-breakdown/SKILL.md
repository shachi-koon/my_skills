# タスク分解

## 概要
設計をもとにタスクを分解し、チケット（Linear/Jira/GitHub Issue）として整理する。

## 分解原則

### 1タスク = 1PR
- 1つのタスクは1つのPRで完結
- レビューしやすいサイズに分割
- 切り戻ししやすい単位

### 粒度の目安
| サイズ | 目安時間 | 特徴 |
|--------|---------|------|
| XS | ~2時間 | 設定変更、小さな修正 |
| S | ~4時間 | 単一機能の実装 |
| M | ~1日 | 複数ファイルにまたがる機能 |
| L | ~2-3日 | 要分割を検討 |
| XL | 3日以上 | 必ず分割 |

### 良いタスクの条件
- [ ] 独立して完了できる
- [ ] テスト可能
- [ ] Done条件が明確
- [ ] 依存関係が明示されている

## タスク構成要素

各タスクに含める項目：

```markdown
## タスク: [タスク名]

### 概要
[何をするか]

### 背景・目的
[なぜやるか]

### Done条件
- [ ] [完了条件1]
- [ ] [完了条件2]

### 確認方法
- [どうやって確認するか]

### 影響範囲
- ファイル: [対象ファイル]
- 機能: [影響する機能]

### 依存関係
- 先行タスク: [なし / #XXX]
- 後続タスク: [なし / #YYY]

### 見積もり
- サイズ: [XS/S/M/L]
- 想定時間: [X時間]

### 同期が必要なドキュメント
- [ ] 設計書の更新
- [ ] APIリファレンスの更新
- [ ] READMEの更新
```

## 進行フロー

### Step 1: 機能単位で洗い出し
設計書から実装すべき機能を列挙。

### Step 2: タスクに分解
各機能を1PR単位のタスクに分解。

### Step 3: 依存関係の整理
タスク間の依存関係を明確化。

### Step 4: 見積もり
各タスクのサイズを見積もり。

### Step 5: 優先順位付け
依存関係と重要度をもとに優先順位を決定。

### Step 6: 承認
**【承認ポイント⑤】タスク確定**
- タスク一覧と優先順位を確認
- 承認なしでは実装に進まない

## チェックリスト
- [ ] すべてのタスクが1PR単位か
- [ ] Done条件が明確か
- [ ] 確認方法が記載されているか
- [ ] 依存関係が整理されているか
- [ ] 見積もりが妥当か（L以上は要分割検討）
- [ ] ドキュメント更新タスクが含まれているか
